# ExampleAPI

**ExampleAPI** — учебный проект на **ASP.NET Core 9**, на примере которого можно разобраться, как устроено серверное REST API на C#.

Приложение имитирует простую систему заказов: пользователи просматривают товары и оформляют заказы, менеджеры управляют товарами, администраторы — учётными записями. Отдельный контроллер демонстрирует загрузку и выдачу файлов.

> **Назначение:** обучение. Проект не рассчитан на публикацию в интернете без дополнительной настройки безопасности.

## Что изучается на примере проекта

- Контроллеры ASP.NET Core: маршруты, HTTP-методы, параметры запроса и ответы.
- Разделение обязанностей между `Controller`, `Service` и `DbContext`.
- DTO для передачи данных и `Result<T>` для результатов бизнес-операций.
- Entity Framework Core, LINQ, связи таблиц и SQLite.
- Асинхронные операции (`async` / `await`).
- Регистрация, хеширование паролей, JWT и авторизация по ролям.
- Swagger UI и загрузка файлов через `multipart/form-data`.

## Быстрый запуск

Потребуется **.NET SDK 9** и Git. Команды выполняются из терминала:

```bash
git clone https://github.com/Getrengen/ExampleAPI.git
cd ExampleAPI/ExampleAPI
dotnet restore
dotnet run --launch-profile http
```

После запуска откройте:

- **Swagger UI:** http://localhost:5239/swagger
- **HTML-документация:** http://localhost:5239/ — если `Description.html` размещён в `ExampleAPI/wwwroot/`.

Адрес `5239` относится к HTTP-профилю из конфигурации проекта. Если приложение сообщает другой URL, используйте его.

### SQLite: куда сохраняются изменения

При старте `SQLiteBdManager.Initialize()` подготавливает рабочую копию тестовой базы. Исходный файл находится в `Infrastructure/TestAPIBD_test_data.db`, а рабочая копия — в папке **`TestAPI` внутри каталога «Документы» текущего пользователя**.

На Windows типичный путь:

```text
C:\Users\<имя_пользователя>\Documents\TestAPI\TestAPIBD_test_data.db
```

**Важно:** существующая рабочая база не заменяется автоматически при каждом запуске. Поэтому при проверке данных и SQL-запросов открывайте именно рабочую копию. Если меняете структуру исходной БД, обновление рабочей копии и модели EF Core нужно продумать отдельно.

**Linux/macOS:** проверьте реализацию `SQLiteBdManager.GetSourcePath()`. Если в ней вручную используются обратные слеши, замените составление пути на `Path.Combine(...)`, прежде чем запускать проект на другой ОС.

## Как устроен проект

```text
ExampleAPI/
├── Controllers/       HTTP-маршруты, атрибуты авторизации, ответы
├── Service/           Бизнес-логика и работа с данными
├── DTOs/              Модели входных и выходных данных API
├── Entities/          Сущности БД, Result<T> и типы результатов
├── Infrastructure/    DbContext, подготовка SQLite и инфраструктура
├── Files/             Пример файлового хранилища
├── wwwroot/           HTML-документация и статические ресурсы
└── Program.cs         Регистрация зависимостей и настройка API
```

Типичный путь запроса:

```text
Клиент / Swagger
       ↓
    Controller      — принимает HTTP-запрос
       ↓
     Service        — проверяет данные и выполняет операцию
       ↓
     DbContext      — обращается к SQLite через EF Core
       ↓
   Result<T>        — результат операции (Success, NotFound и т. д.)
       ↓
 IActionResult      — HTTP-ответ клиенту
```

`Result<T>` описывает итог операции, а `ToActionResult()` преобразует статус результата в HTTP-код. Например, `Success → 200`, `NotFound → 404`, `InvalidData → 400`, `Conflict → 409`. В текущем API создание объектов также отвечает `200`, поскольку отдельный статус `Created` пока не предусмотрен.

## Контроллеры и методы

Маршруты перечислены **в том виде, в котором они объявлены в контроллерах**. `[Authorize]` означает, что требуется JWT; роли должны совпадать с названиями в базе данных.

| HTTP | Маршрут | Доступ | Назначение |
| --- | --- | --- | --- |
| POST | `/api/AuthReg/Register` | Все | Регистрация |
| POST | `/api/AuthReg/Login` | Все | Получение JWT |
| GET | `/api/User/GetAllProducts` | Все | Каталог товаров |
| GET | `/api/User/GetMe` | Авторизованный | Собственный профиль |
| GET | `/api/User/GetOrder` | Авторизованный | Собственные заказы |
| POST | `/api/User/CreateOrder` | Авторизованный | Создание заказа |
| POST | `/api/Manager/AddProduct` | Менеджер | Добавление товара |
| PUT | `/api/Manager/Product/{id}` | Менеджер | Полное изменение товара |
| PATCH | `/api/Manager/Product/{id}` | Менеджер | Частичное изменение товара |
| GET | `/api/Admin/GetAllUsers` | Администратор | Список пользователей |
| PATCH | `/api/Admin/UpdateUserRole` | Администратор | Изменение роли |
| PUT | `/api/Admin/UpdateUser` | Администратор | Изменение данных пользователя |
| POST | `/api/Files/upload` | Все | Загрузка файла |
| GET | `/api/Files/see` | Все | Предпросмотр файла |
| GET | `/api/Files/download` | Все | Скачивание файла |

Здесь **5 контроллеров и 15 HTTP-методов**. Подробные примеры всех запросов приведены в `Description.html`.

## Как проверить API через Swagger

### 1. Зарегистрироваться

Откройте `POST /api/AuthReg/Register`, нажмите **Try it out** и отправьте JSON:

```json
{
  "login": "student01",
  "fullName": "Иван Иванов",
  "passHash": "ExamplePass123"
}
```

Название `passHash` унаследовано от DTO: **передаётся обычный пароль**, сервис самостоятельно преобразует его в хеш. Не используйте реальные пароли для проверки учебного приложения. По умолчанию новая учётная запись получает роль **Пользователь**.

### 2. Получить токен

В `POST /api/AuthReg/Login` отправьте:

```json
{
  "login": "student01",
  "password": "ExamplePass123"
}
```

При успешном входе API возвращает JWT и тип токена `Bearer`. В Swagger нажмите **Authorize** и вставьте сам токен. Затем можно вызвать `GET /api/User/GetMe`.

В обычном HTTP-запросе токен передаётся в заголовке:

```http
Authorization: Bearer <JWT_токен>
```

### 3. Создать заказ

С авторизацией вызовите `POST /api/User/CreateOrder`:

```json
[
  { "productId": 1, "quantity": 2 },
  { "productId": 2, "quantity": 1 }
]
```

Здесь `productId` должен существовать в рабочей БД, а `quantity` должен быть больше нуля. При успехе API возвращает ID созданного заказа. Проверить результат можно через `GET /api/User/GetOrder`.

### 4. Проверить ограничения ролей

Роль обычного пользователя **не даёт доступа** к методам `Admin` и `Manager`. Для тестирования этих контроллеров используйте отдельные учебные учётные записи с нужными ролями. После изменения роли нужно **заново войти**, потому что ранее выданный JWT сохраняет прежнее значение роли.

### 5. Загрузить файл

Метод `POST /api/Files/upload` принимает `multipart/form-data` и поле `file`. После загрузки передайте его имя в `fileName` для `/api/Files/see` или `/api/Files/download`.

## База данных

В SQLite используются пять основных таблиц:

| Таблица | Что хранит |
| --- | --- |
| `Role` | Роли «Администратор», «Пользователь», «Менеджер» |
| `AppUser` | Пользователей, хеши паролей и ссылки на роли |
| `Product` | Названия товаров, цены, описания |
| `Order` | Заказы пользователей и даты их создания |
| `OrderProduct` | Товары внутри заказа и количество |

Связи: `Role → AppUser → Order → OrderProduct ← Product`. Таблица `OrderProduct` реализует связь заказов с товарами и хранит количество каждой позиции.

## Важные ограничения учебной версии

- **JWT-ключ:** сейчас создаётся заново при запуске. После перезапуска потребуется получить новый токен. Для реального сервера ключ должен храниться в защищённой конфигурации.
- **Файлы:** демонстрационная загрузка не должна быть открыта в интернет без ограничений размера, типов файлов и прав доступа. Особенно осторожно относитесь к предпросмотру HTML.
- **Пароли:** не размещайте рабочие логины, пароли, токены и ключи в README или коде.
- **БД:** изменение nullable-свойств в C# само по себе не изменяет структуру SQLite; схему нужно синхронизировать отдельно.
- **Ответы:** текущие `200/400/404/409` отражают выбранную учебную модель `Result<T>`; при развитии проекта можно добавить `201 Created` и `204 No Content`.
- **Запросы:** учётные записи, товары и файлы — учебные данные. Не храните в них персональные или конфиденциальные сведения.
