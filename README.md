# ExampleAPI — учебный REST API на ASP.NET Core

> **Ветка `Test`** · учебный проект на C# и ASP.NET Core 9  

ExampleAPI — пример серверного приложения для работы с пользователями, товарами и заказами. Его основная цель — показать, как организовать Web API на C#: от маршрута HTTP-запроса до работы с базой данных, авторизации и формирования ответа.

Проект предназначен **для обучения**, а не для публикации в открытом интернете без дополнительной проверки безопасности и конфигурации.

## Возможности

- Регистрация и вход, проверка паролей с помощью `PasswordHasher<AppUser>`, JWT-аутентификация.
- Разграничение доступа по ролям **Пользователь**, **Менеджер** и **Администратор**.
- Просмотр каталога, поиск товаров, создание и изменение товаров.
- Создание заказов, просмотр истории собственных заказов и получение заказов сотрудниками.
- Получение информации о пользователях, административное редактирование, изменение роли и собственного пароля.
- **Профиль пользователя**: объединение данных пользователя и его заказов через `ProfileService`.
- Загрузка, просмотр и скачивание файлов как пример работы с `IFormFile`.
- Проверка запросов через Swagger UI.

## Запуск ветки Test

Необходимы **.NET SDK 9** и Git. Команды выполняются в терминале:

```bash
git clone --branch Test https://github.com/Getrengen/ExampleAPI.git
cd ExampleAPI/ExampleAPI
dotnet restore
dotnet run --launch-profile http
```

После старта откройте **Swagger**: [http://localhost:5239/swagger](http://localhost:5239/swagger). Адрес и порт определяются профилем запуска; если в консоли указан другой URL, используйте его.

Для запуска в Rider достаточно открыть решение проекта, выбрать профиль запуска и запустить приложение.

> Ветка `Test` — рабочая учебная ветка. Она может изменяться. При возникновении проблемы сначала проверьте текущие конфигурацию, миграции/схему БД и вывод консоли.

### Как проходит запрос

```text
HTTP-клиент / Swagger
        ↓
Controller — принимает запрос, получает параметры и проверяет доступ
        ↓
Service / интерфейс сервиса — выполняет нужную операцию
        ↓
MyDbContext (EF Core) — читает или изменяет записи SQLite
        ↓
Result<T> — возвращает данные, статус и сообщение
        ↓
ToActionResult() — формирует HTTP-ответ
```

**Контроллеры организованы вокруг ресурсов**, а не по ролям пользователей. Поэтому один `ProductController` предоставляет публичные методы чтения и защищённые методы изменения. Сервисы не обязаны соответствовать строго одной таблице БД: например, `OrderService` работает и с заказами, и с их товарными позициями.

### Зачем нужен ProfileService

`ProfileService` — пример **сервиса-оркестратора**: он использует `IAppUserService` и `IOrderService`, чтобы вернуть единый `ProfileDto` с данными пользователя и списком заказов. Контроллеру не требуется объединять результаты двух сервисов самостоятельно.

```text
ProfileController
       ↓
ProfileService
   ├── IAppUserService → информация о пользователе
   └── IOrderService   → его заказы
       ↓
ProfileDto { User, Orders }
```

## HTTP-маршруты

Ниже перечислены маршруты ветки `Test` на указанном коммите. **Права на изменение** зависят от атрибутов `[Authorize]` и `[Authorize(Roles = "...")]`.

### Авторизация и регистрация — AuthRegController

| HTTP | URL | Назначение | Доступ |
| --- | --- | --- | --- |
| POST | `/api/AuthReg/Register` | Регистрация обычного пользователя | Публичный |
| POST | `/api/AuthReg/Login` | Вход и получение JWT | Публичный |

### Товары — ProductController

| HTTP | URL | Назначение | Доступ |
| --- | --- | --- | --- |
| GET | `/api/Product` | Список товаров | Публичный |
| GET | `/api/Product/{id}` | Товар по ID | Публичный |
| GET | `/api/Product/Search?name=...` | Поиск по названию | Публичный |
| POST | `/api/Product` | Создание товара | Менеджер |
| PUT | `/api/Product/{prodId}` | Полное обновление товара | Менеджер |
| PATCH | `/api/Product/{prodId}` | Частичное обновление товара | Менеджер |

### Заказы — OrderController

| HTTP | URL | Назначение | Доступ |
| --- | --- | --- | --- |
| GET | `/api/Order` | Все заказы | Менеджер |
| GET | `/api/Order/{id}` | Заказ по ID | Менеджер или администратор |
| GET | `/api/Order/My` | Заказы текущего пользователя | Авторизованный |
| POST | `/api/Order` | Создание заказа | Авторизованный |

### Пользователи — AppUserController

| HTTP | URL | Назначение | Доступ |
| --- | --- | --- | --- |
| GET | `/api/AppUser` | Список пользователей | Администратор |
| GET | `/api/AppUser/{userID}` | Пользователь по ID | Администратор |
| GET | `/api/AppUser/Me` | Собственные данные | Авторизованный |
| POST | `/api/AppUser` | Создание учётной записи администратором | Администратор |
| PUT | `/api/AppUser/{userID}` | Обновление пользователя | Администратор |
| PATCH | `/api/AppUser/{userID}/Role?roleId=...` | Изменение роли | Администратор |
| PATCH | `/api/AppUser/Me/Password` | Изменение собственного пароля | Авторизованный |

### Личный кабинет — ProfileController

| HTTP | URL | Назначение | Доступ |
| --- | --- | --- | --- |
| GET | `/api/Profile` | Пользователь и его заказы в одном ответе | Авторизованный |

### Работа с файлами — FilesController

| HTTP | URL | Назначение |
| --- | --- | --- |
| POST | `/api/Files/upload` | Загрузка файла через `multipart/form-data` |
| GET | `/api/Files/see?fileName=...` | Предпросмотр |
| GET | `/api/Files/download?fileName=...` | Скачивание |

> Доступность операций с файлами определяется актуальными атрибутами `FilesController`. Не размещайте демонстрационный файловый API публично без ограничений размера, формата и доступа.

## Примеры работы через Swagger

### 1. Регистрация

Отправьте `POST /api/AuthReg/Register` с JSON-телом:

```json
{
  "login": "student01",
  "fullName": "Иван Иванов",
  "passHash": "ExamplePass123"
}
```

В данном DTO поле `passHash` обозначает **входной пароль**, а не хеш: сервис сам вычисляет и сохраняет хеш. Используйте только тестовый пароль.

### 2. Авторизация

Отправьте `POST /api/AuthReg/Login`:

```json
{
  "login": "student01",
  "password": "ExamplePass123"
}
```

Полученный JWT передайте через кнопку **Authorize** в Swagger. В обычном HTTP-запросе заголовок выглядит так:

```http
Authorization: Bearer <JWT_TOKEN>
```

После этого можно проверить `GET /api/AppUser/Me`, `GET /api/Order/My` и `GET /api/Profile`.

### 3. Создание заказа

В `POST /api/Order` отправьте массив позиций:

```json
[
  { "productID": 1, "quantity": 2 },
  { "productID": 2, "quantity": 1 }
]
```

Идентификаторы товаров должны существовать в базе, а количество — быть положительным. Пользователь определяется сервером из JWT, а не из JSON запроса. Затем вызовите `GET /api/Order/My`.

### 4. Создание и изменение товара

Для методов менеджера нужен токен пользователя с ролью `Менеджер`.

```json
{
  "name": "Механическая клавиатура",
  "price": 3500,
  "description": "Учебный товар"
}
```

Это пример тела `POST /api/Product` и `PUT /api/Product/{prodId}`. Для `PATCH` достаточно передать изменяемое поле:

```json
{ "price": 3200 }
```

### 5. Изменение пароля

Метод `PATCH /api/AppUser/Me/Password` принимает JSON **в теле запроса**, а не в адресной строке:

```json
{
  "oldPassword": "ExamplePass123",
  "newPassword": "NewExamplePass456"
}
```

Не отправляйте пароли в query-параметрах и не записывайте их в логи. Для реального использования нужен HTTPS.

## База данных

Приложение использует SQLite и EF Core. Основные таблицы:

| Таблица | Содержание |
| --- | --- |
| `Role` | Роли пользователей |
| `AppUser` | Учётные записи и хеши паролей |
| `Product` | Каталог товаров |
| `Order` | Заказы пользователей |
| `OrderProduct` | Позиции заказов: товар, заказ, количество |

Связи между данными:

```text
Role ───< AppUser ───< Order ───< OrderProduct >─── Product
```

Исходная учебная БД хранится в `Infrastructure`, а при старте `SQLiteBdManager` может подготавливать рабочую копию в каталоге документов пользователя (`Documents/TestAPI`). **Проверяйте путь к фактически используемой БД**, если изменения не видны в редакторе SQLite. Уже существующая рабочая копия не обязана автоматически перезаписываться при обновлении файла БД в репозитории.

## Result<T> и HTTP-ответы

Сервисы возвращают `Result<T>`, содержащий `Status`, `Data` и `Message`. Через `ToActionResult()` он преобразуется в HTTP-ответ.

| Статус результата | HTTP-ответ |
| --- | --- |
| `Success` | `200 OK` |
| `Created` | `201 Created` |
| `NotFound` | `404 Not Found` |
| `InvalidData` | `400 Bad Request` |
| `Conflict` | `409 Conflict` |

Статус `Created` применяется, если его возвращает соответствующий метод сервиса. Наличие статуса в перечислении не означает, что все POST-методы автоматически возвращают 201.

## Ограничения учебного проекта

- Проект демонстрационный. Перед публичным размещением необходимо провести проверку безопасности JWT, загрузки файлов, авторизации и обработки исключений.
- Не используйте реальные пароли или конфиденциальные сведения в тестовой базе.
- После смены роли уже выпущенный JWT может содержать старую роль до окончания срока действия токена.
- Валидация на уровне DTO и сервисов не заменяет ограничения целостности в самой БД.
- Содержимое HTML-документации (`Description.html`) может относиться к предыдущим версиям API; при расхождении ориентируйтесь на актуальные контроллеры ветки `Test` и Swagger.
